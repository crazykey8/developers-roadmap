**❓ Какое время должен длиться идеальный рабочий цикл: написание теста → изменение функциональности → рефакторинг?**
**✅** Идеальный цикл должен занимать **несколько минут**. Это подход из TDD (Test-Driven Development), где цель — как можно быстрее проходить через цикл:

1. Написал минимальный тест →
2. Реализовал нужный функционал →
3. Провёл рефакторинг, не ломая тест.

---

**❓ Какие библиотеки есть для создания тестов и их запуска (и чем отличаются друг от друга)?**
**✅** Вот популярные библиотеки:

- **Python:**

  - `unittest` — встроенный, строгий, похож на xUnit.
  - `pytest` — гибкий, лаконичный, мощный. Поддерживает фикстуры, плагины.
  - `nose2` — продолжение `nose`, но менее популярен.

- **JavaScript:**

  - `Jest` — всё-в-одном (тест-раннер, мокинг, снапшоты).
  - `Mocha` + `Chai` — гибкая связка, требует настройки.
  - `Vitest` — альтернатива Jest для Vite/ESM-проектов, быстрее.

- **Java:**

  - `JUnit` — стандарт для Java.
  - `TestNG` — более гибкий, ориентирован на сложные сценарии.

Отличаются удобством, производительностью, поддержкой async/await, мокингом, читаемостью вывода и экосистемой.

---

**❓ Как тесты помогают со входом в проект новичков?**
**✅** Тесты демонстрируют **ожидаемое поведение кода**: что должен делать метод, какие входы/выходы. Это как **живые примеры использования** и дают уверенность при изменениях. Новичку проще экспериментировать, не боясь всё сломать.

---

**❓ Как тесты помогают в документировании проекта?**
**✅** Хорошо написанные тесты показывают:

- как использовать API,
- какие кейсы обрабатываются,
- какие ошибки могут возникнуть.

Это **исполняемая документация**, которая всегда актуальна (если тесты проходят).

---

**❓ Как тесты ускоряют получение фидбека от проделанной работы и почему этот фидбек важен?**
**✅** Тесты запускаются за секунды и сразу показывают, работает ли новая логика. Это позволяет **мгновенно видеть ошибки**, не дожидаясь ревью или баг-репортов. Быстрый фидбек критичен для быстрой итерации и уверенности в коде.

---

**❓ Какие этапы ручного тестирования помогают избегать unit-тесты?**
**✅** Unit-тесты автоматизируют:

- проверку граничных случаев,
- проверку обработки ошибок,
- проверку входных/выходных данных.

Это снижает необходимость повторять эти проверки вручную, особенно на уровне функции/модуля.

---

**❓ Зачем добиваться того, чтобы тесты работали быстро, запускались максимально удобно и всего одной командой?**
**✅** Чтобы разработчики **регулярно запускали тесты**. Если тесты запускаются долго или сложно, ими пренебрегают. Быстрый, единый запуск повышает дисциплину и сокращает время от написания кода до его проверки.

---

**❓ Как добиваться того, чтобы ошибки в тестах были максимально очевидными?**
**✅** Рекомендации:

- Использовать **читаемые ассерты** (с понятными сообщениями).
- Делать **один assert на тест**, если можно.
- Давать тестам **говорящие названия**.
- Логировать/показывать контекст при падении.
- Использовать **инструменты форматирования вывода** (`pytest` — хороший пример).

---

**❓ Нужно ли автоматизированно тестировать сами тесты?**
**✅** Обычно — **нет**. Но:

- Если тест содержит сложную логику или нестандартный фреймворк — можно покрыть его вспомогательными тестами.
- Чаще всего достаточно **проверить, что тест ломается, если поменять поведение кода** — это подтверждает его надёжность.

## 🔬 **1. Юнит-тестирование (Jest)**

> Тестируем изолированную логику или компонент без внешних зависимостей.

### ✅ **Кейсы:**

- Проверка отображения данных в компоненте.
- Проверка логики работы кнопок (onClick, onChange).
- Проверка результата функции/утилиты.
- Тестирование кастомных React-хуков.

### 🧩 **Примеры:**

#### A. Компонент отображает имя

```jsx
<MyProfile name="Иван" />
// Ожидаем: на экране есть текст "Привет, Иван"
```

```js
test("отображает имя пользователя", () => {
  render(<MyProfile name="Иван" />);
  expect(screen.getByText(/Иван/i)).toBeInTheDocument();
});
```

---

#### B. Тест утилиты (например, форматирование даты)

```js
formatDate('2025-07-09') → '9 июля 2025'
```

```js
test("форматирует дату", () => {
  expect(formatDate("2025-07-09")).toBe("9 июля 2025");
});
```

---

#### C. Хук useCounter

```js
const { result } = renderHook(() => useCounter());
act(() => result.current.increment());
expect(result.current.count).toBe(1);
```

## 🔗 **2. Интеграционное тестирование (Jest + Testing Library)**

> Тестируем связку компонентов или взаимодействие с API/Redux/Router.

### ✅ **Кейсы:**

- Проверка формы: ввод → отправка → реакция.
- Тестирование модального окна: открылось/закрылось.
- Проверка состояния при переключении табов.
- Интеграция с Redux или React Query.
- Работа с API (через моки).

### 🧩 **Примеры:**

#### A. Отправка формы

```jsx
<Form /> // вводим имя, нажимаем "Отправить", получаем "Спасибо!"
```

```js
test("отправка формы", async () => {
  render(<Form />);
  fireEvent.change(screen.getByLabelText(/Имя/i), {
    target: { value: "Анна" },
  });
  fireEvent.click(screen.getByText(/Отправить/i));
  expect(await screen.findByText(/Спасибо/i)).toBeInTheDocument();
});
```

---

#### B. Работа с Redux

```js
test("увеличивает счетчик через dispatch", () => {
  render(
    <Provider store={store}>
      <Counter />
    </Provider>
  );
  fireEvent.click(screen.getByText("+"));
  expect(screen.getByText("1")).toBeInTheDocument();
});
```

## 🧪 **3. Snapshot-тестирование**

> Проверка, что компонент рендерится одинаково.

### ✅ **Кейсы:**

- Компоненты без логики, только верстка.
- Библиотечные компоненты с пропсами.
- Генерация шаблонов (например, email, PDF).

```js
const tree = renderer.create(<Button label="Купить" />).toJSON();
expect(tree).toMatchSnapshot();
```

## 🧭 **4. E2E-тестирование (Cypress / Playwright)**

> Полное тестирование поведения пользователя в браузере.

### ✅ **Кейсы:**

- Регистрация/логин пользователя.
- Добавление товара в корзину.
- Навигация по сайту.
- Проверка мобильной адаптации.
- Интеграция с бекендом.

### 🧩 **Примеры сценариев:**

#### A. Cypress: покупка товара

```js
cy.visit("/catalog");
cy.get('[data-testid="product-1"]').click();
cy.get('[data-testid="add-to-cart"]').click();
cy.get('[data-testid="cart-count"]').should("contain", "1");
```

## 🎯 **Где тесты особенно полезны:**

- Компоненты с бизнес-логикой (формы, калькуляторы, фильтры).
- Общие утилиты (например, конвертация валют, проверка валидности).
- Многоразовые компоненты (UI-библиотека).
- Сложные формы с валидацией.
- Редко обновляемые модули (тест гарантирует, что они работают как раньше).
